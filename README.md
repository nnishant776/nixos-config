# NixOS / nix-darwin Configuration Flake

A multi-platform configuration flake that manages NixOS, macOS, and standalone Home Manager environments from one repository. Machines are declared under `hosts/`, users can be declared under `hosts/` and `users/`, behaviour is driven by the `conf.*` option tree, and [profiles](#profiles) provide sensible role-based presets that every host can selectively override.

## Repository Layout

```
├── flake.nix                        # entry point: discovers hosts/ & users/, builds configurations
├── lib/
│   ├── mkHost.nix                   # host factory: routes Linux vs Darwin, wires modules
│   ├── buildUser.nix                # user module stack, shared by both HM entry points
│   └── mkUser.nix                   # standalone Home Manager user builder
├── hosts/<machine-name>/            # ONE directory per machine (auto-discovered)
│   ├── hardware-configuration.nix   # Linux only, generated by nixos-generate-config
│   └── default.nix                  # this machine's nixpkgs.hostPlatform and conf.* settings
├── users/<user-name>/               # [OPTIONAL] Per-user definitions (auto-discovered)
│   └── default.nix                  # applied to BOTH standalone and host-integrated HM
└── modules/
    ├── core/                        # shared baseline loaded on every host
    │   ├── base-packages.nix        # canonical CLI tool list (single source)
    │   ├── base.nix                 # installs the baseline (+ bash) system-wide
    │   └── development/             # conf.development packages (Linux + macOS)
    │       └── default.nix · sdk.nix · editors.nix · tools.nix · fonts.nix
    ├── conf/                        # the configuration interface
    │   ├── options.nix              # declares the full conf.* option tree
    │   ├── profile.nix              # profile presets (applied via lib.mkDefault)
    │   └── implications.nix         # e.g. desktop.enable ⇒ multimedia/graphics/...
    ├── user/                        # Base user Home Manager configurations (cross-platform)
    │   ├── default.nix              # base user entrypoint & stateVersion
    │   ├── packages.nix             # cross-platform baseline packages (stdenv conditional)
    │   ├── shell.nix                # cross-platform shell & bash configuration
    │   ├── git.nix                  # git configuration & aliases
    │   └── home-manager.nix         # registers users (adminUser + extraUsers) with HM
    └── system/
        ├── linux/                   # NixOS implementation of conf.*
        │   ├── base.nix             # NixOS-only infra: PATH vars, nix-index, nix-ld
        │   ├── host.nix             # hostname, users, group grants from conf.host
        │   ├── locale.nix           # i18n from conf.host.locale
        │   ├── development/         # conf.development nix-ld export (Linux-only)
        │   ├── services/            # conf.systemServices.*, one file per service
        │   └── desktop/             # conf.desktop.*  ⇒ apps, fonts, shells
        └── darwin/                  # macOS implementation (settings)
```

## How Configuration Works

Adding a machine or standalone user requires no changes to `flake.nix`:

1. **Create `hosts/<machine-name>/`** containing:
   - `hardware-configuration.nix` — Linux hosts only (from installer).
   - `default.nix` — sets `nixpkgs.hostPlatform` and the machine's `conf.*` configuration.
2. **Evaluate/build Host**:
   ```bash
   nixos-rebuild   switch --flake .#<machine-name>   # Linux
   darwin-rebuild  switch --flake .#<machine-name>   # macOS
   ```
3. **Evaluate/switch Standalone Home Manager**:
   ```bash
   home-manager switch --flake .#<username>         --impure   # this machine
   home-manager switch --flake .#<username>@<host>  --impure   # explicit host
   ```
   `--impure` is required: resolving the bare `<username>` reads the running
   machine's hostname. The `<username>@<host>` form skips that lookup and is the
   one to use off-machine or on macOS, where `/etc/hostname` does not exist.

### Two domains

Configuration in this flake splits along ownership, and the split is deliberate:

**Organisation domain** — infrastructure and security policy: disk encryption,
Secure Boot, SSH daemon settings, firewall, package sources, nix settings, audit
and log shipping, sudo policy. All of it system-level, all of it in `modules/` and
`hosts/`, and all of it fair game for compliance assertions.

**User domain** — window manager, shell, theming, editors, personal packages.
Owned by the user, *not* organisation policy, and not something this flake tries
to dictate. A user's own configuration lives in their `~/.config/home-manager/`
and is applied by standalone Home Manager, which they run themselves.

So `conf.desktop.environments.<name>.enable` decides which environments a host
*makes available* (enable several to install them all), and
`conf.desktop.defaultEnvironment` only picks the greeter's preselected/default
session — neither forces which one a user must use.

Per-user configuration reaching the *system* build comes from three in-flake
layers only:

| Layer | Source | Applies to |
|---|---|---|
| baseline | `modules/user/` | every managed user (declared with `lib.mkDefault`) |
| per-user | `users/<name>/default.nix` | every user of that name |
| per-host | `conf.host.*.extraHomeConfig` | that user on that host |

`~/.config/home-manager/default.nix` is **never** read during a system rebuild.
A rebuild evaluates as root, so a user-writable file there would get root's read
access, and the same flake revision would stop producing the same closure on
every machine. Standalone Home Manager reads it; the system build does not.

`enableHomeManager` therefore decides who owns a user's home directory. Do not
set it `true` and also have that user run standalone Home Manager: both write the
same dotfiles and share the same Home Manager profile state, so each activation
undoes the other's files. Pick one owner per user.

#### Organisation policy inside the home directory

Some settings live in a home directory but *are* infrastructure or security
policy, and those do belong to the organisation domain. They go in
`modules/user/` (fleet-wide) or `users/<name>/` (one user), never in the user's
own `~/.config/home-manager/`.

This list is deliberately open — add to it as policy is decided:

| Candidate | Why it is policy, not preference |
|---|---|
| git commit signing + allowed signers | provenance of committed code |
| SSH client config | agent forwarding, host key checking, control-master reuse |
| gpg-agent / ssh-agent cache lifetimes | credential exposure window |
| git / tooling credential helpers | keeps secrets out of plaintext on disk |
| shell history policy | secrets landing in a world-readable history file |
| per-user `nix.conf` (`nix.settings`) | substituters and trusted keys are a supply-chain surface |
| user-side agents (backup, posture reporting) | must exist and keep running |

Contrast with things that are **not** policy and should stay with the user:
window manager and compositor config, theming, colour schemes, editor choice and
keybindings, shell prompt, personal packages.

How to express one once decided:

1. Declare it in `modules/user/` for everyone, or `users/<name>/` for one user.
2. Use a plain value if a user may adjust it; `lib.mkForce` if they may not.
3. Verify the *merged* result with a system-level assertion, because a user
   module can out-prioritise any value but cannot touch assertions declared at
   the NixOS/nix-darwin level.

Keep in mind what this does and does not buy. Home Manager writes files into a
directory the user owns, so `mkForce` plus an assertion guarantees what gets
*delivered*, not what is on disk a minute later. Runtime enforcement needs a
mechanism outside Home Manager — dconf locks on Linux, MDM managed preferences on
macOS — and anything else is detected by posture reporting rather than prevented.

> A new `users/<name>/default.nix` must be `git add`-ed before Nix can see it.
> Flakes only read files git knows about, so an untracked user module is silently
> ignored rather than reported as an error.

`lib/mkHost.nix` assembles the module stack. These are peers, not a precedence
ladder — the numbering is reading order only:

| Layer | Module | Role |
|---|---|---|
| 1 | `hosts/<name>/default.nix` | your settings (plain assignments, so they beat every `mkDefault` below) |
| 2 | `modules/core` | cross-platform baseline: CLI tools, dev tooling |
| 3 | `modules/conf` | option declarations + profile presets + implications |
| 4 | `modules/user/home-manager.nix` | Home-Manager wiring for each enabled user |
| 5 | `modules/system/linux` *or* `modules/system/darwin` | platform implementation of `conf.*` |

### Users & Home-Manager

`conf.host.adminUser` (plus optional `conf.host.extraUsers`) drives both the OS
accounts (`host.nix`) and Home-Manager users (`home-manager.nix`). Users with
`enableHomeManager = true` get the shared config in `modules/user/`, anything in
`users/<name>/default.nix`, and their `extraHomeConfig`. Users with
`enableHomeManager = false` manage their own home with standalone Home Manager.
Group membership is granted
automatically: `video`/`input` (desktop), `docker`/`podman` (containers),
`libvirtd`/`kvm` (VMs), `networkmanager` (networking).

## Option Reference (`conf.*`)

### `conf.host`

| Option | Type | Default | Description |
|---|---|---|---|
| `host.name` | str | `"localhost"` | Hostname |
| `host.timezone` | str | `"Asia/Kolkata"` | Timezone |
| `host.locale` | str | `"en_IN"` | Locale (also sets all LC_* vars) |
| `host.adminUser` | user submodule | `{}` | Primary user (see below) |
| `host.extraUsers` | list of user submodule | `[]` | Additional accounts |

User submodule fields:

| Field | Type | Default | Description |
|---|---|---|---|
| `name` | str | `"admin"` | Username |
| `fullName` | str | `"Administrator"` | Full name (used for git) |
| `email` | str | `""` | Git email (falls back to `<name>@localhost`) |
| `groups` | listOf str | `[ "wheel" ]` | Extra groups (platform groups are auto-added) |
| `initialHashedPassword` | str | *(hash)* | Initial password — change after install |
| `enableHomeManager` | bool | `true` | Register this user with Home-Manager |
| `extraHomeConfig` | deferredModule | `{}` | Extra per-user HM configuration |

### `conf.profile`

One of `minimal` · `server` · `workstation` · `developer` · `gaming` · `embedded`
— see [Profiles](#profiles).

|---|---|---|---|
| `desktop.enable` | toggle | `false` | GUI stack, display managers |

### `conf.development`

Top level:

| Option | Type | Default | Description |
|---|---|---|---|
| `development.enable` | toggle | `false` | Master switch for the dev stack |
| `development.extraPackages` | listOf package | `[]` | Always-installed dev extras (plus `uv`) |

Each SDK (`sdk.base`, `sdk.cpp`, `sdk.go`, `sdk.rust`, `sdk.python`, `sdk.java`,
`sdk.nix`, `sdk.cue`, `sdk.lua`) and each CLI tool (`tools.gemini`, `tools.opencode`,
`tools.rtk`) shares this shape:

| Field | Type | Default | Description |
|---|---|---|---|
| `enable` | toggle | `false` | Install this group |
| `packages` | listOf package | `[]` | **Replaces** the curated default package set |
| `extraPackages` | listOf package | `[]` | **Appends** to the default set |
| `nix-ldLibraries` | listOf package | `[]` | Runtime libs exported to nix-ld |

Editors follow the SDK shape plus config-source fields:

| Editor | Extra fields |
|---|---|
| `editors.neovim` / `editors.emacs` | `configPath` (str, local path), `configRepo` (str, remote) |
| `editors.vscode` | standard fields only |

## Profiles

Profiles are **one-line role presets**. Setting `conf.profile = "<role>"`
enables a coherent bundle of services and tools — every value is applied with
`lib.mkDefault`, i.e. *weakly*, so any host setting wins automatically.

| Profile | Enables |
|---|---|
| `minimal` | networking |
| `server` | networking · containerisation · virtualisation · development + `sdk.base` |
| `workstation` | networking + wifi · multimedia · graphics · desktop · powerManagement · flatpak |
| `developer` | *workstation set* + containerisation + virtualisation + development (`sdk.base…lua`, neovim, emacs) |
| `gaming` | *workstation set* (multimedia/graphics/desktop included) |
| `embedded` | networking + development + `sdk.base` + `sdk.cpp` |

Notes:
- `developer` enables **all SDKs and neovim/emacs**, but not `editors.vscode`
  nor any `tools.*` — enable those per host if wanted.
- `gaming` currently mirrors the workstation service set; add game launchers via
  `desktop.extraPackages`.
- Enabling `desktop` anywhere also pulls in multimedia/graphics/power/flatpak
  (weak implication).

Usage — just set it in the host config:

```nix
# hosts/my-server/default.nix
{
  nixpkgs.hostPlatform = "x86_64-linux";
  conf.profile = "server";
}
```

## Overriding Profile Defaults Per Host

Because presets use `lib.mkDefault` (priority 1000) and plain host assignments
use priority 100, **any value you write in a host config silently wins** — no
special syntax required. Toggle something off, swap an enum, extend lists:

```nix
# hosts/my-laptop/default.nix
{ config, pkgs, lib, ... }: {
  nixpkgs.hostPlatform = "x86_64-linux";

  conf = {
    profile = "developer";                    # start from the preset...

    host.name = "MY-LAPTOP";

    systemServices = {
      containerisation.enable = false;        # ...but no Docker/Podman here
      graphics.vendor = "nvidia";             # preset assumed Intel; pick NVIDIA
    };

    desktop = {
      environment = "hyprland";               # not "all"
      environments.hyprland.shell = "caelestia";
      extraPackages = with pkgs; [ discord spotify ];
    };

    development = {
      sdk = {
        go.enable = false;                    # don't need Go on this box
        python.extraPackages = [ pkgs.black ];# append to Python's default set
      };
      tools.opencode.enable = true;           # profile leaves tools off by default
    };

    host.adminUser.extraHomeConfig = {        # per-user Home-Manager additions
      programs.alacritty.enable = true;
    };
  };
}
```

Rules of thumb:

| You want | Use |
|---|---|
| Override a value a module set with `lib.mkDefault` (all profile presets) | plain assignment |
| Override a value a module set with a *plain* assignment | `lib.mkForce` — two plain definitions are a conflict error, not a win |
| Beat another module's `lib.mkForce` | `lib.mkOverride 40` — lower number wins; two `mkForce`s conflict |
| Append to a list option | `extraPackages`, or a plain list assignment — list definitions concatenate |
| Replace a curated list rather than appending to it | the declaring module has to use `lib.mkDefault`; otherwise both definitions merge |

Priority decides these, never import order or position in a tier list: `mkDefault`
is 1000, a plain assignment is 100, `mkForce` is 50, and the lowest number wins.
Two definitions at the same priority are an evaluation error unless the option's
type merges them (lists concatenate, attrsets merge, scalars do not).

Because any definition can be beaten by a lower `mkOverride`, this ordering is a
convention for keeping configuration readable — not a boundary that stops someone
from overriding organisation defaults. See the comment in `lib/buildUser.nix`.

Inspecting final values without switching:

```bash
nix eval .#nixosConfigurations.my-laptop.config.conf.systemServices.graphics.vendor
```
